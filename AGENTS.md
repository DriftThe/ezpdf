# AGENTS.md

ezpdf — a Tauri 2 desktop **real-time PDF translation reader** for Windows, built with Vue 3 + TypeScript + Vite. See `PLAN.md` for the approved architecture and phased plan (OCR via an in-repo Python FastAPI service, LLM translation, Rust-side scheduling; both reader panes are self-drawn with `pdfjs-dist` — do not reintroduce pdf-vue3). Current state: UI skeleton + real repo IPC, no mock data. Repo model = `.ezrepo` flat index (`{folders, pdfs[]}`, pretty JSON; each entry `{id, name, bind, belong}` — `id` is a content-hash stable unique key generated at import time, the key for all frontend lookups; `bind` = bound-JSON repo-relative path). Multi-file import via `import_pdf` (best-effort, returns `ImportOutcome {imported, failed}`; copies PDFs in as `<name>-<id>.pdf` + skeleton `<name>-<id>.json`, rejects duplicate content by hash). Repo mutations (2026-09-14): `create_folder`/`delete_folder`/`delete_pdf`/`move_pdf` return the updated `RepoTree` (frontend applies it in place — no refresh command anymore); folders are **logical** (`belong` label only, nothing on disk), so `move_pdf(belong=null)` = move out to root and `delete_folder` **cascades** (deletes the folder's PDFs + bind JSONs — the confirm dialog says so); the sidebar's 新增文件夹 button replaced the old 刷新仓库 button and RepoTree row menus (hover) drive move/delete and the row has a dedicated 清除解析状态 button (refresh icon; delete confirms via the in-app `ConfirmDialog.vue` + `composables/confirm.ts`, **not** plugin-dialog anymore; 清除解析状态 → `reset_pdf_state` rebuilds the 1..=N empty skeleton, drops all OCR blocks and translations, returns `Pending`, frontend drops its cache/reloads the book and wakes the scheduler — `total` comes from pdfjs `reader.pageCount` for the open book and `0` otherwise, in which case the backend reuses the page count already in the JSON). The chosen repo is persisted (`repo` key in config.json) and auto-opened on launch (`library.openLastRepo()`, clears the path when it fails); 导入 PDF/新增文件夹 are disabled with no repo, and the sidebar footer has a 选择 button to re-pick. **Bound JSON is the user-defined single source of truth** for parse state: `{status: "Pending"|"Processing"|"Finished", pages: [{index (1-based), finished, translated, blocks: [{type, content, loc: [x1,y1,x2,y2] corners in pt, translation}]}]}`. Import pre-fills the pages skeleton (index 1..N, `finished/translated: false`, empty `blocks`; N is parsed from the bytes via lopdf — parse failure (e.g. encrypted PDF) falls back to `pages: []` and the reason surfaces through `ImportOutcome.warnings` in the import toast). `translation: null` does NOT mean hidden — it means render `content` as-is: the LLM returns null when it judges the translation to be the same language as the source; `translated` marks the LLM pass done for that page (serde default false → old JSONs auto-backfill translation). Translation-pane overlay rule (user-decided 2026-09-11; formula added 2026-09-12; footer/vision_footnote added 2026-09-14; **type set made user-configurable 2026-09-15**): the type set lives in `src/lib/blocks.ts` (`BLOCK_TYPE_OPTIONS`/`DEFAULT_TRANSLATED_TYPES` = text/paragraph_title/doc_title/abstract/aside_text/footnote/footer/vision_footnote/figure_title/content) — the option list is every label except image (the 10 defaults first, then reference/reference_content/algorithm/number/header/chart/seal/**table**, unchecked by default - table is opt-in since 2026-09-16; `formula` is never a translate choice, it is always covered as KaTeX) and is persisted as `general.translateTypes` (checkboxes in 设置→常规) and passed per-invoke as `LlmConfig.translateTypes` — the checked types (plus formula) get a white-bg overlay box showing `translation ?? content` (bypass stage → original content); unchecked types and all others (table/chart/image/number/header/seal/algorithm/reference/reference_content) get NO overlay — original PDF pixels show through, their OCR content lives only in the bound JSON; an empty `translateTypes` means the built-in default on both sides, and a change only affects pages that are not translated yet (already-translated pages keep their JSON, so 清除解析状态 is the way to re-run them); overlay font size auto-fits the box (binary-search largest fitting size, fill without overflow) via the `v-fit` directive in PageCard.vue; **tables** (user 2026-09-16) are not a text cover: the markup stream (`<fcel>/<ecel>/<lcel>/<ucel>/<xcel>/<nl>`) is parsed **in Rust only** (`src-tauri/src/table.rs` -> `block.grid` = cells with `colspan`, short tail rows right-padded, `<ucel>/<xcel>` become blank cells, unparsable markup -> no grid -> no translate, no cover), sent to the LLM as `{"table": [[cell...], ...]}` in `Q` (result must be a same-shaped 2-D array under `A`/`content`, validated per row; a mismatch fails the whole page per the user decision, and the per-book strike budget is the fallback), stored as a JSON matrix string in `translation` with `A=null` meaning "already in the target language" -> the **source matrix** is written instead so the block is terminal, and rendered by `reader/TableCover.vue` (CSS grid with colspan, KaTeX per cell, binary-search font fit; if even the minimum font overflows the cover goes transparent so the original pixels show); formula covers are vertically centered with the KaTeX display margins trimmed (`.cover-formula` — KaTeX's default 1em margins otherwise eat a ~16pt formula box and shrink the fit); 换行符渲染成 `<br>`（`renderRichText` 的 `textToHtml`，覆盖框与悬浮卡片共用；用户 2026-09-15 反馈目录块在译文栏被压成一段——OCR 的 `content`/`translation` 本来就带 `\n`，是 HTML 默认把它折叠了，所以老页面无需重跑；提示词规则 5 另外要求模型在目录这类结构化块里把丢失的换行补回来）。Stage-2 rendering shipped: pdfjs-dist v6 canvas pages (self-virtualized), asset-protocol fetch, real page count/geometry, fit-width zoom; translation pane shows EmptyState while `bind === null || status === "Pending"`. Settings are a full-page overlay (not a modal); repo-tree rows are intentionally large (~1.3x default). Zoom is viewport-anchored (`ReaderPane.vue` captures the midpoint page + in-page fraction before zoom/geometry reflows and restores it after; `overflow-anchor: none` so the browser's native anchoring doesn't fight it — zoom no longer jumps pages). Cover text padding scales with box size (small boxes keep usable font sizes). Linux/system-proxy story aside, the app ships a self-drawn window chrome (2026-09-14): `decorations: false`, a 34px `TitleBar.vue` carrying only the `ezpdf` wordmark, the light/dark/system theme toggle and minimize/maximize/close (drag via `data-tauri-drag-region`, double-click maximizes, red hover on close; window defaults to 1600×1022). Theme is `general.theme` (persisted; applied by `composables/theme.ts` through `:root[data-theme]` with a temporary `.theme-switching` color fade — light is blue-white, and `index.html` pre-applies a localStorage mirror to avoid a first-paint flash). Startup defaults to **paused** (toolbar shows 启动翻译) unless both 自动唤醒 OCR and 自动续跑 are on (both default off — 2026-09-15 fixed; the store shipped them as `true`, contradicting this line). LLM settings are a **pi-ai provider/model preset picker** (2026-09-15): a vendored copy of `@mariozechner/pi-ai`'s model catalog (`src/lib/piModels.generated.ts`, refreshed by `node scripts/sync-pi-models.mjs`) drives a provider dropdown + searchable model list with capability/cost badges, filling the endpoint and deriving the wire protocol + thinking-off shape + max-tokens field; 验证 probes connectivity (and the thinking-off strategy for custom endpoints) and `/models` is fetched **on click only**; GitHub releases are checked at launch (silent) and via 常规 → 检查更新.

## Commands

Package manager is **pnpm** (no lint or test scripts exist yet).

- `pnpm dev` — Vite dev server only (frontend in browser); first runs `scripts/copy-pdfjs-assets.mjs`
- `pnpm build` — typecheck + build (`vue-tsc --noEmit` + copy script + `vite build`); this is the typecheck command
- `pnpm tauri dev` — full desktop app dev (starts Vite automatically via `beforeDevCommand`)
- `pnpm tauri build` — release build/bundle (Rust release profile uses LTO, strip, panic=abort); `beforeBuildCommand` also runs `scripts/pack-runtime.mjs` (stages the bundled Python + pyserver + prompts into `src-tauri/resources/`, cached across builds — set `EZPDF_PYTHON_PKG` if the download is unavailable)
- Rust checks: run `cargo check` / `cargo build` inside `src-tauri/`; `cargo test` also regenerates ts-rs bindings
- `node scripts/sync-pi-models.mjs` — refresh the vendored pi-ai model catalog (`src/lib/piModels.generated.ts`) from npm (`--latest` to follow the newest release, `--check` to verify); needs no network at build/run time after that

## Architecture

Two halves, communicating only through Tauri's IPC:

- `src/` — Vue 3 frontend (`<script setup>` SFCs). Entry `src/main.ts` (installs Pinia); app shell is `src/components/shell/AppShell.vue`. UI state lives in Pinia stores under `src/stores/` (library/reader/parse/settings); domain types mirror the Rust serde structs via ts-rs bindings re-exported in `src/types/domain.ts`. `src/lib/piModels.ts` wraps the generated pi-ai catalog (`piModels.generated.ts`, do not hand-edit) with provider labels/ordering, `detectProviderId` migration and the persisted preset compat snapshot.
- i18n (user 2026-09-15): **vue-i18n 11** (`legacy: false` + `globalInjection`, installed in `main.ts`), three locales 简中/繁中/English. Catalogs live in `src/locales/parts/` (`common`/`shell`/`reader`/`settings`/`pipeline`), assembled by `src/locales/index.ts`; each part goes through `helpers.defineMessages()`, which makes the **zh-CN key set authoritative** — adding a key in one language and forgetting another is a compile error. Components use `const { t } = useI18n()`; non-component code (stores/composables) imports `t()` from `src/lib/i18n.ts`, which also owns `detectLocale()` (`navigator.language` → zh-CN / zh-TW for hant|tw|hk|mo / en, everything else falls back to en), the `ezpdf.lang` localStorage mirror (read before mount so the first paint isn't in the wrong language), `setLocale()` and `defaultTargetLang()`. The picker sits in 设置 → 常规 and persists `general.lang` (saved like the theme, immediately); 目标语言 is a **preset dropdown** (`src/lib/languages.ts`: value = the English name written into the prompt, label = native + English name so it needs no catalog entry, plus a 自定义 entry that swaps in the free-text input) — `settings.ts`'s `ensureLoaded()` defaults `general.lang` and an empty `llm.targetLang` from the **system language** (user decision 2026-09-15: an English OS gets target language `English`) — keep those defaults outside the "config.json exists" branch, a bare `if (!text) return;` used to skip them on first launch (found by smoke test). Provider display labels stay data in `piModels.ts` (Chinese map for zh-CN/zh-TW, catalog English otherwise) rather than message keys.
- Rendering pipeline (stage 2): import pdfjs ONLY via `src/lib/pdfjs.ts` (worker setup + `openPdf()` which injects the runtime resource paths — cMaps/standard fonts/wasm/ICC; skipping them breaks CJK text and non-embedded standard fonts). `src/composables/usePdfDoc.ts` caches one `PDFDocumentProxy` per pdf id; `ReaderArea.vue` owns the doc lifecycle (load / destroy / switch-race guards). Page-list truth = pdfjs `numPages` (reader store `pageCount` falls back to bound-JSON `pages.length`); card geometry is per-page real (`reader.pageSizeFor(n)`, measured in background chunks by ReaderArea after doc ready — scan PDFs often have a different size on every page, so overlays must divide loc by the SAME per-page viewport the OCR capture used; page-1-based assumption caused whole-page misalignment, fixed 2026-09-11); the bound JSON supplies only OCR block overlays (`PdfPageCard`/`PdfPageCanvas` self-virtualize via IntersectionObserver). Original-pane block rects are hover targets: a translated block pops a teleported rich-text card (`hover-preview`, fixed follow-cursor; `above` flips upward in the lower viewport half) — deliberately NOT a `title` attribute (user 2026-09-14). PDF binaries never travel through invoke — the frontend fetches `convertFileSrc(pdfPath)` asset URLs.
- Settings (`src/components/settings/`): `SettingsPage.vue` is an absolute overlay in `AppShell` (z-10) covering sidebar+reader with `v-show` — nothing underneath unmounts; the top toolbar (z-20, height `--toolbar-h`) stays visible. Sections are registered in the `SECTIONS: Record<SettingsSection, ...>` map — extending the union without registering is a build error (`llm`/`ocr`/`common`; the old 解析 pane is gone — its concurrency fields were dead and its resume switch moved into 常规). Per-section components live in `settings/sections/` (pure markup, no scoped CSS; root element uses `set-pane`), state lives in the settings store, back button = save-and-exit (no per-pane save buttons and **no success toast** — the page just closes; save = `save_settings` writes pretty JSON to `config.json` = repo root in dev / **app directory (beside the exe) in production on Windows, `~/.ezpdf/config.json` elsewhere** (`prod_settings_path`; a deb/rpm install dir is root-owned and an AppImage is read-only) — and closes; the store `ensureLoaded()` reads it once at startup AFTER the dev-only `auth.cfg` fill so persisted values win, and **every write is a whole-file write gated by a `loaded` flag** — saving before a successful load (or after a failed one) is refused with a console error / `settings.saveNotLoaded` toast, since it would wipe the user's config; the `save_settings` failure mode was hit for real on 2026-09-15 (settings snapshotted default `general.lang`/`llm.targetLang` over the user's file); malformed sections are ignored field-by-field; legacy `ocr.autoLaunch`/`parse.resumeOnStart` keys migrate to `general`). 常规 holds 启动时自动唤醒 OCR 服务 (`general.autoLaunch`) and 启动时自动续跑 (`general.resumeOnStart`): `AppShell` onMounted sets `parse.paused = true` unless BOTH are on, then `parse.autoStartIfEnabled()` probes env and only calls `ocr_start` when Python/deps/models are all present (log line instead of a crash loop otherwise), plus 检查更新 (`check_update` → GitHub releases of DriftThe/ezpdf; launch check is silent, manual toasts errors). Shared form classes `.set-pane/.set-title/.set-field/.set-field-row/.set-check/.set-hint/.set-button` are global in `main.css` (`set-` prefix, don't combine `.set-button` with `.btn`). LLM pane (2026-09-15, pi-ai preset integration): 供应商 is a dropdown fed by `src/lib/piModels.ts` — usable presets (models whose pi-ai `api` is `openai-completions`) first, then 协议暂不支持 (identify-only), then 自定义; picking a provider fills its Base URL and auto-selects the first usable model, 预设模型 is a searchable list with badges (思考/图像/api/上下文/价格) and clicking a row applies it; unsupported-protocol providers are NOT listed in the dropdown (only `openai-completions` presets + 自定义; a saved config pointing at one shows as a disabled entry) — the why and the per-protocol work needed are written down in `docs/protocols.md`; `llm.provider` + `llm.preset` (derived compat snapshot: `api`/`thinkingFormat`/`thinkingOffKind`/`thinkingOffValue`/`maxTokensField`/`reasoning`/`extraHeaders`) are persisted so a cold start needs no catalog load; the catalog chunk (~400KB) is lazy-imported on first UI/migration use; legacy configs (baseUrl only) are migrated by `detectProviderId` reverse-matching the endpoint. API Key row still has 验证 (`verify_llm` → connectivity + thinking-off probe, writes `llm.thinkingOff`; strategy `none` warns unless the preset says the model is non-reasoning), model input stays a datalist fed by 获取在线列表 / `fetch_llm_models` (for new models not yet in the catalog).
- `src-tauri/` — Rust backend. `src-tauri/src/pyenv.rs` owns ALL pyserver path resolution (the single dev/prod branch point, `cfg(dev)` compile-time + `EZPDF_TOOLKIT_ROOT`/`EZPDF_PYTHON_EXE`/`EZPDF_MODELS_DIR` runtime overrides; resolved once in the `setup` hook and stored as global `PyPaths` state) plus the environment layer: on Linux the install directory is read-only, so `PyPaths` splits the bundled interpreter (`base_python`, read-only, also what `probe_blocking` reports before the venv exists) from the service interpreter (`python` = `~/.ezpdf/venv/bin/python3`, created on first 一键安装服务 from the bundled one via `venv_dir`; Windows keeps installing into the writable per-user install directory, dev uses `pyserver/.venv`). `probe_blocking()` runs `pyserver/bootstrap.py` (pure-stdlib probe → one-line stdout JSON contract in PLAN-pyserver.md §6) with the bundled python (prod, `<install>/python/python.exe`) or the dev venv / discovered system python (`py -3` → `PATH python`); models live outside the install dir in prod (`~/.ezpdf/models`, so upgrades don't re-download 1.9GB). `install_env(mode, use_mirror)` is the one-click service install (user 2026-09-14): returns `Ok(true)` and does nothing when deps are complete and the torch build already satisfies the pick (CUDA ⊂ CPU — a cuda env answers a cpu request, never the reverse); GPU mode aborts up front when `nvidia-smi` is missing, otherwise base requirements → torch variant chosen by the dropdown (installed-cuda skips reinstall), streaming both pip streams to `ocr://log` plus staged progress (`ocr://install` {phase, percent}, mirrored to frontend) — the mirror switch swaps in TUNA pypi + SJTU pytorch-wheels for the official indexes (`pip --retries 6 --timeout 60`; TUNA has dropped a download mid-flight); the **CPU variant takes the `/cpu` wheel index off Windows** because PyPI's Linux torch wheel silently bundles CUDA (measured 5.1GB with nvidia-*/triton vs 1.4GB from the cpu index — and its metadata version has no `+cu` tag, which is why `bootstrap.py` also falls back to an nvidia-*/triton presence check). `download_models(use_mirror)` adds the model layer: `requirements-download.txt` (huggingface_hub only, installed on demand — idempotent pip) → `python -m app.fetch`, which snapshot-downloads the missing models (`PaddlePaddle/PP-DocLayoutV3_safetensors`, `PaddlePaddle/PaddleOCR-VL-1.6`) through `hf-mirror.com` (mirror on) or `huggingface.co` (off) into `EZPDF_MODELS_DIR` — skip-if-complete with the same completeness contract as bootstrap, resumable by the hub library. `src-tauri/src/pyserver.rs` owns the service lifecycle state machine (`supervise`: spawn `python -m app.main` → wait `EZPDF_READY {port,pid}` stdout line (60s) → `/health` with the per-spawn session token → connected; crash → exponential-backoff restart, 3 consecutive → `failed` terminal; stop = drop the held child stdin → Python's stdin-EOF watchdog self-exits); a second, child-less mode (`set_remote`/`disconnect`, user 2026-09-15) points `ocr_target()` at a **remote parse service** the user configured (`ocr.mode`/`ocr.url`/`ocr.token` in 设置→OCR 服务, `ocr_start_remote(url, token)` probes `/health` with the token then registers the endpoint, `ocr_health(url, token)` is the read-only 测试 button; the token is the server-side shared secret used by the container/bare-metal entry `python -m app.server_docker`, which resolves it as `EZPDF_TOKEN` env > `EZPDF_TOKEN_FILE` (`token.txt`, default `<pyserver>/token.txt`) > generate+persist, prints it on every start and enforces it on all routes including `/health`) — the protocol a compatible server must implement (endpoints, payloads, px↔pt contract, lifecycle, batch-size negotiation) is written down in `pyserver/PROTOCOL.md`, and `pyserver/server_test.py` starts such a service locally on 9055 for development (`--max-batch N` to advertise a smaller batch, `--token` to test the guard). **Never run `docker builder prune` / `docker system prune` on the dev machine**: the BuildKit cache holds the torch/nvidia wheels, and clearing it forces a multi-GB re-download (the user is often on metered data). The Dockerfile already mounts apt + pip caches (`--mount=type=cache`) so editing an upper layer re-uses them. Build args `BASE_IMAGE`/`APT_MIRROR`/`PIP_INDEX`/`TORCH_INDEX` exist because Docker Hub, deb.debian.org and download.pytorch.org are all slow/blocked in mainland China (verified working mirrors: `docker.m.daocloud.io`, `mirrors.tuna.tsinghua.edu.cn`, `mirror.sjtu.edu.cn/pytorch-wheels/{cpu,cu132}`). Measured: CPU image ~6GB reported / 3.6GB content, GPU ~12.5GB reported / 7.3GB content (models baked in on purpose - the container must work with no volume and no network, e.g. an air-gapped server). Do **not** trim packages for size: the image is meant to be a faithful package of the verified env, and torch's CUDA build hard-links its nvidia-* deps (ldd shows libnccl/libcusparseLt/libnvshmem/libcupti as needed even for single-GPU eager inference). Container images: `pyserver/Dockerfile` (one file, `--build-arg VARIANT=cpu|gpu`) + `pyserver/docker-compose.yml` (`docker compose --profile cpu|gpu up -d --build`, models ~1.9GB baked in via `COPY models`, `token.txt` on the `./data` volume, default host bind 127.0.0.1:9055; the torch CUDA deps come from pip's nvidia-* wheels so no nvidia/cuda base image is needed). `/health` advertises `max_batch_pages` (from `EZPDF_MAX_BATCH_PAGES`, default 32 = the same value `/ocr/pages` accepts); the frontend asks for it **before every OCR batch** and the local managed mode keeps its own fixed 4. Production packaging: `scripts/pack-runtime.mjs` stages a relocatable python-build-standalone 3.12 (bare, pip only) + pyserver code + system_prompt into `src-tauri/resources/` (mirror chain NJU → ghfast → GitHub; cache + `EZPDF_PYTHON_PKG` override; bsdtar explicitly, PATH tar may be MSYS GNU tar) and hard-fails if `dist/` contains the `auth.cfg` apiKey; `tauri.conf.json` maps `resources/*` into the install root (`bundle.resources` targets are relative to the resource dir → `<resource dir>/python` etc.; on a deb that is `/usr/lib/ezpdf/{python,pyserver,system_prompt}`, verified by installing the package — prod `PyPaths` probes that first, falling back to a `resources/` subdir), `bundle.targets: ["nsis"]` with `--bundles deb,rpm` overriding it on Linux, `installMode: currentUser` so pip can write the Windows install dir. Commands registered in `generate_handler![]`: `check_and_build_repo`, `gettree_from_config`, `load_pdf`, `import_pdf`, `create_folder`, `delete_folder`, `delete_pdf`, `move_pdf`, `load_settings`, `save_settings`, `ocr_env_report`, `ocr_install_env`, `ocr_download_models`, `ocr_start`, `ocr_stop`, `ocr_health`, `ocr_start_remote`, `parse_pdf`, `translate_pdf`, `prefill_pages`, `reset_pdf_state`, `verify_llm`, `fetch_llm_models`, `check_update`; events `ocr://status` (payload = ServiceStatus string), `ocr://log`, `ocr://install` (InstallProgress) and `llm://log` (translation-chain log → rendered at the bottom of the LLM settings pane). Invoked from the frontend with `invoke("command_name", {...})` from `@tauri-apps/api/core`. Command args are camelCase in JS and snake_case in Rust; serde structs serialize **camelCase** as well (the TS field is `pdfPath`, not `pdf_path`).
- OCR scheduling bridge (stage 4 批3; decoupled translation 2026-09-14): the parse store drives the loop entirely frontend-side — single `tick()` = pick book (focused first; per-book `load_pdf` reads bind JSON status/finished/translated flags, no parse_progress command) → ring-collect ≤batch-size unfinished pages (focused book starts at `reader.currentPage`, others at 1; batch size = the client's 4 in managed-local mode, or the `max_batch_pages` the online service advertises — re-read with a `/health` handshake before every online batch, user 2026-09-15) → `src/lib/pageCapture.ts` offscreen render (PNG b64, scale 2.0) → invoke `parse_pdf` (OCR only — it no longer waits for translation) → per-book translation chain: `queueTranslate` fire-and-forgets `translate_pdf` for the just-OCR'd pages (same book serializes, Rust runs stride-2 phases internally), so the next OCR batch starts immediately. Results patch `library.pdfs[id].pages` for the focused book (translation pane updates reactively; background books have no store cache — Rust's atomic tmp+rename batch write is the truth, next round re-reads via load_pdf). The chain self-continues via queueMicrotask after each batch; nothing processable → `standing` suspends; wakes fire from library.selectPdf / importPdf success / loadRepo / serviceStatus→connected watch / unpause / prefill completion / a drained translation chain with untranslated pages left. Per book, translate-retry outranks new OCR (2026-09-14 fix): a `finished && !translated` page whose chain is idle gets translated before more OCR; **table backfill** (user 2026-09-16) rides the same chain: `load_pdf` parses+persists the missing `block.grid` for table blocks (one write per book, under the per-book file lock), and a page that IS translated but still holds a parsable untranslated table becomes a translation target too (frontend `needsWork` = `needsTranslation || needsTableBackfill`; Rust `build_task` then collects **only** that page's tables, so same-language blocks that legitimately stay `null` are never re-sent) — otherwise an OCR batch persisted right before a quit was never retried while the book still had OCR work. Separate OCR/translation strike maps: 3 failures of one kind suspend only that kind for the book (OCR keeps running with a broken LLM, and vice versa); only external wakes reset the budgets (`wake(false)` = chain-drain self-continuation keeps them). `parse.paused` (toolbar 暂停翻译/启动翻译) gates the whole loop: `tick()` via `isRunnable()` (= `canOcr() || canTranslate()` — user 2026-09-15 split the old single gate so a basic environment without torch/models/services can still translate pages whose OCR text already exists; `pickBook` only returns OCR targets while the parse service is connected) and `queueTranslate`/its `run` refuse new submissions while paused (in-flight invoke finishes; resume via `togglePaused` → `wake`). `usePdfDoc` is LRU≤2 with a pin for the focus book (never evicted); background books reuse the same per-id cache. Books with empty pages (lopdf parse failure) are skipped until opened — geometry-ready watch backfills via `prefill_pages` then wakes. Non-Tauri browser mode (`pnpm dev` without Tauri): silently inert.
- LLM translation (stage 4 批4, 2026-09-14): spec/decisions in `PLAN-LLM.md`. `src-tauri/src/translate.rs` is the OpenAI-compatible client + smart-context agent loop: per page it packs TRANSLATED_TYPES blocks (non-empty content, `translation == null`) into protocol A, allows ONE `need_context` round (context C from the neighbour page's boundary ≤3 blocks, before=tail/after=head), validates `result` 1:1 by index (A=null = same-language), and binds a valid `external`/`external_index` back onto the neighbour page's block (that box is then skipped on its own page via `translation != null`; fallback format B or a bad index touches nothing). Thinking is disabled per provider, in this precedence (2026-09-15): explicit `thinkingOff` strategy → the empirically verified endpoint rules (zen: `reasoning.enabled=false` + `reasoning_effort=none`; SiliconFlow: `enable_thinking=false` + `thinking.type=disabled`) → the pi-ai preset shape derived from the selected model (`thinkingOffKind`/`thinkingOffValue`: `thinking_type` for deepseek, `enable_thinking` for zai/qwen, `chat_template_kwargs`, `reasoning_effort` for openrouter/openai-with-off-value, `none` = nothing); `modelReasoning: false` skips thinking params entirely (matrix in PLAN-LLM.md §5). `parse_batch` is OCR-only (one atomic write) — the parse store chains `translate_pdf` per OCR batch; `translate_pdf` runs stride-2 phases (positions 0,2,4… then 1,3,5…, so neighbouring pages never translate concurrently) with per-page tasks on snapshots (`build_task`/`translate_task`/`apply_done`) over `tauri::async_runtime::spawn`, then re-reads the JSON under the per-book file lock (`FILE_LOCKS` in `parse.rs`; network/LLM calls stay outside the lock) and merges. `LlmConfig.translateEnabled` (user 2026-09-15, 设置→LLM 首项「启用翻译」) adds a no-network path: `apply_bypass` writes each translatable block's `content` into `translation` and marks the page `translated`, so the OCR text reaches a terminal state instead of staying null (re-enabling translation later must not re-translate it; the frontend sends a payload even with no keys configured, which is what lets a bare install "finish" OCR work). `LlmConfig` also carries the pi-ai preset snapshot (`provider`/`api`/`thinkingFormat`/`thinkingOffKind`/`thinkingOffValue`/`maxTokensField`/`modelReasoning`/`extraHeaders`, all `#[serde(default)]` so old configs keep working): `chat_request` **rejects any `api` ≠ `openai-completions`** with a clear message (other protocols are identify-only for now), picks the max-tokens field name (`max_completion_tokens` when the preset says so), applies `extraHeaders`, and `verify_llm` short-circuits to a no-probe success when `modelReasoning == false` (`presetNoThinking` → no warning toast). System prompt = `<prompt dir>/intelli_context.md` for smart mode, `standard_translate.md` for `smartContext` off (no context protocol at all; result items use `content` — the parser accepts both `A` and `content`, and non-smart tasks ignore any stray `need_context`; `{{target_language}}` templated at load; if the placeholder is missing the target language is appended — user 2026-09-14; `EZPDF_SYSTEM_PROMPT_DIR` overrides the dir — the one place to change for packaging; prod resolves it from the bundled `system_prompt/` resource). Thinking-off is a persisted strategy (`llm.thinkingOff`: `auto` = preset shape / URL rules, `reasoning`/`enable_thinking`/`thinking_type` explicit, `none` = plain) discovered by the LLM pane's 验证 button (`verify_llm` probes with a short prompt and checks `reasoning_content`/`reasoning`/empty content; if nothing works it warns 无法关闭思考模式 and stores `none`; non-reasoning presets skip the probe). LLM config arrives per-invoke from the settings store, dev-filled from gitignored root `auth.cfg` via a Vite raw import (`loadAuthCfg` in `src/stores/settings.ts`, dev-only; `pack-runtime.mjs` additionally greps `dist/` for the key and aborts the build if found); reqwest needs `rustls-tls` + `system-proxy` (defaults are off — the system proxy is how region-restricted endpoints are reached, and `ProxyOverride` keeps local pyserver direct); opencode zen endpoints also get an `x-opencode-session` routing header scoped by URL (see PLAN-LLM.md §5). Custom reasoning: 提示词协议改动要与 `translate.rs` 的解析同步。Rust 侧与 `pyserver/`（Python）侧的**日志与错误文案一律英文**（用户 2026-09-15：中文日志不合适），但**发给模型的提示词保持中文**——`PROBE_PROMPT`/`CORRECTION`/`NO_MORE_CONTEXT`/`load_system_prompt` 的目标语言兜底句是模型输入而非界面文案，i18n 时不要顺手翻译（会改变模型行为）。

## Gotchas

- **Port 1420 is strict** (`vite.config.ts`): Vite fails if it's taken, and `tauri.conf.json` points `devUrl` at it. HMR uses 1421 when `TAURI_DEV_HOST` is set.
- **`src/lib/piModels.generated.ts` is generated** — never hand-edit; refresh with `node scripts/sync-pi-models.mjs` (it vendors only pi-ai's data module + a ported copy of its non-exported `detectCompat`, so re-diff the port whenever the pi-ai version changes). The catalog is identify-only for protocols other than `openai-completions`.
- **`testfiles/` is gitignored** and reserved for manual-test PDFs (text+table+formula+image). It is no longer referenced by code; the reader renders PDFs from the library store (real repo data via IPC only — mock data was removed).
- **Asset protocol** (`tauri.conf.json` → `security.assetProtocol`): enabled with an intentionally **empty static scope**; `gettree_from_config` grants the repo root at runtime via `asset_protocol_scope().allow_directory(root, true)` (least privilege). Requires the `protocol-asset` cargo feature on `tauri` (already set). If a render shows "PDF 加载失败", suspect a missing scope grant first.
- **pdfjs v6 API breaks**: `PDFDocumentProxy.destroy()` no longer exists — release via `doc.loadingTask.destroy()`; `page.render()` requires `canvas` (not just `canvasContext`).
- **pdfjs runtime assets** (`cmaps`/`standard_fonts`/`wasm`/`iccs`) are copied to `public/pdfjs/` by `scripts/copy-pdfjs-assets.mjs` (runs at the start of `pnpm dev`/`pnpm build`). `public/pdfjs/` is gitignored — regenerated on first dev/build, never hand-edit. Without them CJK text renders misplaced/missing.
- Vite is configured to not watch `**/src-tauri/**` — Rust changes require restarting `pnpm tauri dev`.
- Windows dev machine: the Rust lib is named `ezpdf_lib` (with `_lib` suffix) to avoid a Windows bin/lib name conflict — keep the suffix.
- TypeScript is strict with `noUnusedLocals`/`noUnusedParameters`; unused imports will fail `pnpm build`.
- No CSP is set (`"csp": null` in `tauri.conf.json`) — fine for dev; if a CSP is added later, pdfjs needs `worker-src` for its module worker.
- The build warning about a >500 kB chunk is expected (pdfjs-dist is large); code-split later if it matters.
- Legacy hand-written test entries in a repo (files not named `<name>-<id>.pdf`) will fail to load/render by design — re-import them.
- Running `vite` directly (not via `pnpm dev`/`pnpm build`) skips the pdfjs asset copy — a fresh clone then misses `public/pdfjs/` and CJK rendering degrades (404s in console, no crash).
- **pyserver/** is the ported Wise-Paddle OCR service host (stage 2.5; decisions in PLAN-pyserver.md §2.1). Single-instance pipeline (`PP-DocLayoutV3` + `PaddleOCR-VL-1.6` in `app/services/pipeline.py`, lazy-loaded + `threading.Lock`) — concurrency containers (Pool/Scheduler/vouchers) were deliberately degenerated away; don't reintroduce them. `models/` is a direct copy of Wise-Paddle's model dir (1.9GB, gitignored) but is not a hard prerequisite — on a fresh host `app/fetch.py` (`python -m app.fetch`, invoked by `ocr_download_models`) downloads the missing repos via hf-mirror with resume; completeness = config.json + preprocessor_config.json + any weight file (same contract as bootstrap.py; both honour `EZPDF_MODELS_DIR`, so the prod model lights read `~/.ezpdf/models`). Requests are bounded before they can hurt: 64 MB body (Content-Length check in `main.py` before the body is read), 12k px side / 40 MP per image with decoding on the threadpool and `DecompressionBombError` caught (`routers/ocr.py`). `requirements-download.txt` is `huggingface_hub` only, installed on demand. `requirements.txt` is a verified-minimal set; the four non-obvious pins are load-path requirements, not optional: `protobuf` (SentencePieceExtractor; without it the VL tokenizer is misdetected as a tiktoken file and fails to parse), `sentencepiece` + `tiktoken` (PaddleOCR-VL tokenizer), `opencv-contrib-python` (PP-DocLayoutV3 post-processing). The VL tokenizer loads without `trust_remote_code` — the rope patch in `pipeline.py` (ported, module-level side effect) must stay. Layout detection is multi-pass add-only (`LayoutDetector.detect`): main pass unchanged at threshold 0.5, then a sharpened pass at 0.45 merges text-family candidates, then sharpened top/bottom half-page tiles at 0.38 (header/footer also allowed) merge more — fixes systematic misses of small/spaced text under pdfjs rendering (pdfium renders score ~0.1-0.15 higher on the same line; full-page squash to 800x800 compresses tall pages, tiles undo it; tuned 2026-09-12, see PLAN-OCR.md §8.4; candidates must pass IoU ≤0.3 and containment ≤0.6 against existing boxes; `BoxFilter.min_score` is 0.35 to let them through; all model forwards are chunked to ≤4 images because batch=8 hits a slow kernel). `BoxFilter.filter` also drops 大框套小框 duplicates (user 2026-09-14): after NMS, a box substantially contained (≥60% of its area, `contain_threshold`) in an already-kept larger box is discarded — NMS can't catch nesting because IoU is tiny. Two entries: `app/main.py` (managed: ephemeral port + `EZPDF_READY` line + stdin-EOF watchdog, token comes from `EZPDF_TOKEN` injected by Rust) and `app/server_docker.py` (deployed/container: binds `EZPDF_HOST:EZPDF_PORT`, default `0.0.0.0:9055`, **no** watchdog — a container's stdin is `/dev/null` and would kill it instantly — and resolves its own token via `config.resolve_token()`: `EZPDF_TOKEN` > `EZPDF_TOKEN_FILE` (default `<pyserver>/token.txt`) > generate+persist, printed on every start for the client's 服务令牌 field).
- `parse.ts` store: `serviceStatus` (incl. `failed`) is driven by the `ocr://status` event, `envReport`/`envLogs` by `ocr_env_report`/`ocr://log`, `installProgress` by `ocr://install`, `llmLogs` by `llm://log` (Rust `translate::log` + frontend `[ui]` 调度日志；LLM 设置页底部 `log-box`）；the OCR settings pane's five lights (Python/CUDA/环境/模型/服务) derive from these — don't add separate probe commands. `installService(mode, useMirror)` chains `ocr_install_env` (bool = 已安装跳过) → `ocr_download_models` only when models are missing (`installing` guards reentry).
- Frontend `listen()` subscriptions in `parse.ts` reject silently outside the Tauri runtime (plain `pnpm dev` browser mode) — keep the `.catch(() => undefined)`.

## 版本与发布

版本唯一真相源 = `src-tauri/tauri.conf.json` 的 `"version"`（安装包名、`app.package_info()`、前端 `getVersion()`、更新检查全部读它）。

双语 README（用户 2026-09-15）：`README.md`（简体中文，正式书面语）+ `README.en.md`（英文），两页顶部互切；英文截图占位 `docs/screenshot.en.png`（用户提供后替换占位文字）。README 内含「路线图」小节记录两项未决事项：**代码签名**（计划申请 [SignPath Foundation](https://signpath.org/) 的 OSS 免费签名——证书签发给 SignPath Foundation 自身、HSM 托管、每次发布需人工审批；Azure Artifact Signing 因 Public Trust 仅限美/加个人与美/加/欧/英组织而不可用）与 **AppImage**（随机路径只读挂载会让随包解释器派生的 venv 失效，需先把解释器复制到 `~/.ezpdf/python` 再建 venv；用户决定先记账不做）。

1. **改版本**：编辑 `src-tauri/tauri.conf.json` → `"version": "0.2.0"`（可选同步 `package.json` 便于 npm 侧识别；`Cargo.toml` 的 version 不参与打包）。
2. **构建**：仓库根执行 `pnpm tauri build`。自动执行：`vue-tsc` 类型检查 → `vite build` → `scripts/pack-runtime.mjs`（随包 Python/pyserver/提示词，已缓存则秒过；改 Python 版本需删 `src-tauri/resources/.runtime-stamp` 或 `--force`）→ Rust release（LTO）→ NSIS 打包。Linux 上同一条命令出 deb/rpm（需系统依赖 `libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev patchelf libayatana-appindicator3-dev`，用 `--bundles deb,rpm` 覆盖 `bundle.targets`）。
3. **产物**：Windows `src-tauri/target/release/bundle/nsis/ezpdf_<version>_x64-setup.exe`（~25MB）；Linux `bundle/deb/ezpdf_<version>_amd64.deb` 与 `bundle/rpm/*.rpm`（首次运行后在应用内「一键安装服务」下载依赖与模型）。
4. **分发**：把安装包传到 GitHub Releases，tag 用 `v<version>`（如 `v0.2.0`）——应用内「检查更新」查 `DriftThe/ezpdf` 的 latest release 并按 tag 比数字版本。
5. **CI（推荐）**：`git push` tag `v<version>` 即触发 `.github/workflows/release.yml`（matrix：windows-latest / ubuntu-22.04 + `tauri-apps/tauri-action@v1`，`pnpm install --frozen-lockfile` → tauri build → NSIS / deb+rpm），产物进 **draft** Release；先跑 `check-version` 卡 tag 与 tauri.conf 版本一致。冒烟后手动 publish（`gh release edit v0.2.0 --draft=false`）——draft/预发布不会被「检查更新」看到。注意 CI 里没有 `auth.cfg`（`pack-runtime.mjs` 的密钥断言自然通过），Python 运行时由镜像链在 runner 上现下（~50MB）。
6. **注意**：安装包未签名（用户首次运行会有 SmartScreen 提示，需代码签名证书才能消除）；`pack-runtime.mjs` 会在构建时校验 `dist/` 不含 `auth.cfg` 的 apiKey，发现即中止构建。**Linux 已在 WSL2（Ubuntu 26.04 + WSLg，非 CI 的 22.04）实测通过**：`cargo test` 42/42、`pack-runtime` 打 stripped 运行时（staged 83MB / deb 70MB）、`--bundles deb,rpm` 出包、`dpkg -i` 装后可启动、生产路径解析符合设计（资源根 `/usr/lib/ezpdf`、`base_python` 只读、服务解释器 `~/.ezpdf/venv/bin/python3`、设置落 `~/.ezpdf/config.json`）、从随包解释器建 venv 并 `pip install` 基础依赖 + torch CPU（1.4GB）、只读安装目录下用 venv 起 pyserver（`EZPDF_READY` + `/health` + token 403 + 关 stdin 自退）。**仍未验证**：GUI 层的 JS 冒烟（WebKitGTK 没有 CDP，要驱动得走 `tauri-driver` + `webkit2gtk-driver`）、真点一次「一键安装服务」按钮、模型下载（1.9GB）与 Linux 上的真实 OCR 推理、以及 CI 的 ubuntu-22.04。AppImage **暂不发布**：它是随机路径的只读挂载，venv 的 `pyvenv.cfg` 每次挂载都会失效（要支持得先把随包解释器复制到 `~/.ezpdf/python` 再建 venv）。
